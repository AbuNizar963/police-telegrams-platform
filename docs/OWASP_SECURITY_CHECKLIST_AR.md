# قائمة التحقق الأمنية وفق OWASP — منصة برقيات الشرطة

هذه القائمة مرجع عملي لمراجعة التغييرات الأمنية، وليست شهادة امتثال أو بديلاً عن اختبار اختراق مستقل. تُطبّق على الويب والخادم وتطبيق Flutter وقاعدة البيانات والتخزين وخطوط البناء.

## 1. قبل التعديل: نموذج التهديد

- [ ] تحديد الأصل المحمي: حساب، برقية، مرفق، جهة، تقرير، رمز جلسة أو إعداد.
- [ ] تحديد الممثلين: مستخدم عادي، مدير جهة، مسؤول منصة، مستخدم غير مصادق، ومستخدم من جهة أخرى.
- [ ] تحديد حدود الثقة: المتصفح/الهاتف، API، الخادم، Supabase، التخزين، وخدمات الطرف الثالث.
- [ ] تحديد سيناريوهات الإساءة والأثر المتوقع، بما فيها تسريب البيانات والتلاعب والحذف وتعطيل الخدمة.
- [ ] تحديد السلوك المسموح والمرفوض واختبارات إثباته.

## 2. OWASP Top 10 — نقاط الفحص

### A01 — كسر التحكم بالوصول
- [ ] التحقق من الصلاحية في الخادم لكل endpoint وعملية قراءة/تعديل/حذف/تصدير/رفع/تنزيل.
- [ ] التحقق من ملكية المورد والعضوية النشطة في الجهة عند كل طلب.
- [ ] اختبار BOLA/IDOR بتبديل معرفات البرقيات والمرفقات والجهات بين مستخدمين مختلفين.
- [ ] مراجعة صلاحيات المدير ومسؤول المنصة ومبدأ أقل صلاحية.
- [ ] مراجعة RLS وViews وRPC وSECURITY DEFINER وعمليات service-role.

### A02 — الإخفاقات التشفيرية
- [ ] عدم حفظ كلمات المرور أو PIN كنص صريح؛ استخدام KDF مناسب وتخزين آمن على الجهاز.
- [ ] فرض HTTPS في الإنتاج وخصائص Cookie الآمنة.
- [ ] حماية المفاتيح والأسرار وعدم تضمين service-role أو مفاتيح سرية في العميل.
- [ ] تدوير/إبطال الجلسات بعد تغيير كلمة المرور والخروج والحوادث وفق نموذج الجلسات.
- [ ] عدم تسجيل رموز الجلسات أو الروابط الموقعة أو البيانات الشخصية الحساسة.

### A03 — الحقن
- [ ] استخدام استعلامات مهيأة/ORM آمن وعدم تركيب SQL من مدخلات المستخدم.
- [ ] ترميز المخرجات لمنع XSS وHTML injection، خصوصاً معاينة البرقيات والمرفقات.
- [ ] التحقق من مسارات الملفات وأسماءها ومحتوى الاستيراد والتصدير.
- [ ] فحص CSV formula injection عند إنشاء ملفات قابلة للفتح في جداول البيانات.

### A04 — التصميم غير الآمن
- [ ] وجود حدود معدل ومحاولات فاشلة لواجهات الدخول واستعادة الحساب وPIN.
- [ ] تحديد حدود الحجم والوقت والصفحات والتزامن والعمليات المكلفة.
- [ ] مراجعة إساءة استخدام إعادة إرسال الطلبات والروابط الموقعة وتكرار العمليات.
- [ ] عدم الاعتماد على إخفاء عناصر الواجهة أو قفل محلي لحماية بيانات الخادم.

### A05 — الإعدادات الأمنية الخاطئة
- [ ] مراجعة CORS وCSRF وCSP وSecurity Headers وخصائص Cookies.
- [ ] عدم تخزين استجابات API الخاصة في Cache أو Service Worker أو CDN.
- [ ] مراجعة سياسات التخزين والروابط العامة/الموقعة وصلاحيات قاعدة البيانات.
- [ ] تعطيل وضع التصحيح والرسائل التفصيلية والأسرار في الإنتاج.

### A06 — المكونات الضعيفة أو القديمة
- [ ] مراجعة تنبيهات الاعتماديات وملفات lock وتحديثات الأمان.
- [ ] فحص حزم Node وFlutter وأدوات البناء وGitHub Actions.
- [ ] مراجعة التغييرات في الاعتماديات والـ lifecycle scripts ومصادر الحزم.

### A07 — إخفاقات المصادقة
- [ ] مراجعة دورة التسجيل والدخول والخروج وتغيير كلمة المرور واستعادة الحساب.
- [ ] منع التخمين باستخدام rate limiting/backoff دون قفل دائم يتيح حجب الخدمة.
- [ ] التأكد من رفض الرموز القديمة بعد الإبطال، لا الاكتفاء بمسح Cookie.
- [ ] حماية جلسات الهاتف والتخزين المحلي وعدم اعتبار App Lock مصادقة خادمية.

### A08 — إخفاقات سلامة البرمجيات والبيانات
- [ ] حماية CI/CD بأقل صلاحيات وعدم كشف الأسرار لطلبات fork غير الموثوقة.
- [ ] مراجعة مصدر الاعتماديات وسلامة lockfiles والأدوات والإصدارات.
- [ ] التحقق من ملفات الاستيراد والمرفقات بالتوقيع الفعلي للمحتوى، لا MIME وحده.
- [ ] مراجعة مسارات الإصدار والتوقيع وبناء Android وiOS.

### A09 — إخفاقات التسجيل والمراقبة
- [ ] تسجيل أحداث الدخول وتغيير الصلاحيات والرفع والتنزيل والحذف والتصدير.
- [ ] عدم تسجيل أسرار أو محتوى البرقيات أو بيانات شخصية كاملة.
- [ ] إضافة معرف تتبع آمن للأخطاء وربط الحدث بالمستخدم والجهة عند الحاجة.
- [ ] التأكد من أن فشل سجل التدقيق يعالج وفق حساسية العملية ولا يخفي فشلها.

### A10 — تزوير الطلبات من جانب الخادم SSRF
- [ ] حصر وجهات URL الخارجية المسموح بها عند جلب موارد من الخادم.
- [ ] رفض مخططات غير HTTP/HTTPS والوجهات الداخلية وعناوين loopback/link-local/private.
- [ ] التحقق من التحويلات redirects وDNS rebinding والوجهة النهائية.
- [ ] عدم قبول روابط رفع/تنزيل يحددها العميل دون تحقق.

## 3. مراجعة المرفقات والتخزين — اختبارات إلزامية

- [ ] مستخدم الجهة A لا يستطيع إصدار رابط أو قراءة أو حذف مرفق الجهة B.
- [ ] لا يمكن إعادة استخدام رابط رفع لمورد/جهة أخرى.
- [ ] لا يمكن اعتماد المرفق قبل التحقق من الحجم والنوع والتوقيع والملكية.
- [ ] الرابط الموقّع محدود المدة والغرض ولا يكشف المفتاح أو يسمح بتجاوز الصلاحيات.
- [ ] رفض البروتوكولات غير الآمنة في الإنتاج، والتحقق من Host والوجهة.
- [ ] فحص صلاحيات التنزيل والتصدير والمعاينة بعد تغيير العضوية أو تعطيل الجهة.

## 4. Supabase وقاعدة البيانات

- [ ] RLS مفعّل لكل جدول في schema مكشوف، والسياسات تعكس نموذج الصلاحيات الفعلي.
- [ ] UPDATE policy تحتوي USING وWITH CHECK عند الحاجة لمنع نقل ملكية الصف.
- [ ] Views لا تتجاوز RLS دون قصد؛ مراجعة security_invoker وامتيازات الوصول.
- [ ] كل SECURITY DEFINER محصور ومراجع وله search_path مضبوط وصلاحيات EXECUTE ضيقة.
- [ ] كل استخدام service-role يسبقُه تحقق خادمي صريح من المستخدم والجهة والمورد.
- [ ] اختبار migrations وقواعد البيانات على بيئة محلية/اختبارية قبل الإنتاج.

## 5. متطلبات الاختبارات وGitHub Actions

- [ ] اختبار إيجابي للمستخدم المصرح واختبار سلبي للمستخدم غير المصرح.
- [ ] اختبار عزل الجهات والـ IDOR ورفع/تنزيل/حذف المرفقات.
- [ ] اختبارات الجلسات القديمة بعد logout وتغيير كلمة المرور.
- [ ] تنسيق وتحليل أنواع واختبارات وبناء الإنتاج لكل فرع متأثر.
- [ ] مراجعة CI وCodeQL وSecret Scanning وDependency Review عند تغير الاعتماديات.
- [ ] فحص كل Actions على commit النهائي لكل فرع؛ لا تعتبر pending/cancelled نجاحاً.
- [ ] مراجعة diff كاملاً لمنع حذف اختبارات أو تعطيل ميزات أو إضافة تجاوزات.
- [ ] توثيق الفحوص الفاشلة والمتخطاة والمخاطر المتبقية وعدم الادعاء بنجاح غير مثبت.

## 6. سجل نتيجة كل مراجعة

لكل نتيجة، سجّل:
- الشدة: حرجة / عالية / متوسطة / منخفضة / ملاحظة.
- الملف والمسار والسطر أو endpoint المتأثر.
- سيناريو الاستغلال والأثر.
- الإصلاح والاختبار الذي يمنع عودة المشكلة.
- حالة التحقق: ناجح / فاشل / لم يُنفذ / غير منطبق.
- المخاطر المتبقية والقيود.

**قاعدة الدمج:** لا يُدمج تغيير أمني قبل نجاح الفحوص المطلوبة على الالتزام الدقيق، ومعالجة النتائج الحرجة والعالية، ومراجعة الفرع المقابل عند وجوده.
