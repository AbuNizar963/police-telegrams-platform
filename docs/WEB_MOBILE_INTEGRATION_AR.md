# نموذج تطوير الويب وتطبيق الهاتف على فرعين

## القرار المعماري

الويب وتطبيق Flutter عميلان للنظام نفسه، وليسا خادمين أو قاعدتي بيانات منفصلتين. يحتوي `main` موقع الويب وخادم API ومخطط البيانات، وهو مصدر نشر الإنتاج. يحتوي `flutter-mobile-app` تطبيق Flutter وفحوص الهاتف، إضافة إلى نسخة متوافقة من ملفات الخادم والأنواع المشتركة اللازمة لاختبار عقد API. يتصل الهاتف بخادم الإنتاج نفسه عبر API/tRPC، ولا يتصل بقاعدة Supabase مباشرة ولا يحمل سرًا إداريًا.

فصل الفرعين يفصل دورة تطوير الهاتف عن نشر الويب، لكنه لا يفصل المصادقة أو الصلاحيات أو بيانات البرقيات. يظل خادم `main` المرجع النهائي للتحقق من الهوية والعضوية والجهة وحالة البرقية. نسخة الخادم الموجودة في فرع التطبيق مخصّصة للتوافق والاختبار، وليست مصدر نشر مستقلًا.

يبقى تعريف `.github/workflows/flutter-mobile.yml` في `main` لأن GitHub يتطلب وجود ملف workflow الذي يستخدم `workflow_dispatch` في الفرع الافتراضي. محفزات البناء وطلبات الدمج وإصدار Android مقيّدة إلى `flutter-mobile-app`؛ لذلك لا يؤدي push إلى `main` إلى بناء التطبيق أو نشر APK.

## مسؤوليات الفروع

- **`main`:** المصدر المعتمد لموقع الويب وAPI والخادم ومخطط البيانات، ونشر Vercel للإنتاج. لا يحتوي مجلد تطبيق Flutter `mobile/`.
- **`flutter-mobile-app`:** المصدر المعتمد لتطوير Flutter ومجلد `mobile/` واختباراته وCI الخاص به. يحتفظ بنسخة متوافقة من ملفات الخادم والأنواع المشتركة لاختبار عقد tRPC.
- **وسم الاستعادة:** حُفظ الرأس السابق للتطبيق في `archive/flutter-mobile-app-pre-separation-0341b018`؛ هذا وسم وليس فرعًا.

لا تُحذف واجهات API التي يحتاج إليها الهاتف من الخادم لمجرد فصل مجلد التطبيق. عند تغيير API أو المخطط أو الصلاحيات، تُراجع التغييرات على `main` أولًا، ثم تُزامن إلى `flutter-mobile-app` عبر تغيير مراجَع، وتُشغّل الفحوص المناسبة على الفرعين. لا تدمج فرع التطبيق إلى `main` لمجرد إصدار Android.

## دورة التغيير والإصدار

1. تغييرات الويب والخادم تبدأ من `main` وتُراجع عبر PR إلى `main`؛ نشر Vercel للإنتاج مرتبط بهذا الفرع.
2. تغييرات Flutter تبدأ من `flutter-mobile-app`. تُشغّل فحوص CI وFlutter وCodeQL وفحص الأسرار، وتُراجع توافقات API عند تغيير العقد.
3. يجب أن تبقى قواعد التفويض في الخادم؛ إخفاء زر في الهاتف أو الاعتماد على التخزين المحلي لا يمثل حاجزًا أمنيًا.
4. إصدار Android إجراء يدوي منفصل من `flutter-mobile-app` بعد نجاح الفحوص وتوفر إعدادات التوقيع والجاهزية. لا ينشر push أو PR إصدارًا عامًا تلقائيًا.
5. لا تُزامن تغييرات الخادم إلى فرع الهاتف إلا بعد مراجعة التوافق وحل التعارضات واختبار الطرفين؛ ولا يُدمج الهاتف إلى `main`.

## الاعتماديات والأمان

تنبيهات Dependabot وميزة automated security fixes وSecret Scanning مفعّلة على المستودع. أُوقف إنشاء PRs الاعتيادية لتحديث إصدارات npm وGitHub Actions، ووُضع `open-pull-requests-limit: 0` في إعداد Pub الموجود في فرع التطبيق لإيقاف التحديثات الاعتيادية حيث ينطبق الإعداد. تبقى تحديثات الأمان منفصلة؛ قد ينشئ إصلاح أمني عاجل فرعًا أو PR مؤقتًا، ولا ينبغي تعطيله لمجرد الحفاظ على عدد الفروع.

**قيد مهم لتطبيق الهاتف:** ملف `dependabot.yml` الذي يعتمده GitHub يوجد في الفرع الافتراضي. وبما أن ملفات Flutter موجودة فقط في `flutter-mobile-app`، فإن إعداد Pub في نسخة هذا الفرع لا يضمن وحده إنشاء Dependabot security PRs لتبعيات Flutter. ينبغي مراجعة Dependency Graph/Dependabot alerts للتطبيق دوريًا، أو اعتماد ماسح مستقل يعمل على فرع الهاتف إذا لزم أتمتة تغطية Pub بالكامل. لا تُعتبر حدود الفروع بديلًا عن مراجعة الاعتماديات.

تعطيل التحديثات الاعتيادية لا يوقف مراجعة الاعتماديات في PRs ولا يُغني عن معالجة تنبيهات الثغرات. راجع كذلك [دليل Secret Scanning ونطاق الفروع](SECRET_SCANNING_BRANCH_SCOPE_AR.md)؛ لا يمكن استخدام مرشحات Gitleaks لإيقاف Secret Scanning الأصلي المدمج في GitHub.

## التوافق والبيانات

يوجد اختبار عقد ساكن على فرع الهاتف يطابق أسماء إجراءات tRPC التي يستدعيها Flutter مع `appRouter`. هذا الاختبار لا يثبت تطابق الحقول أو الصلاحيات أو السلوك الكامل؛ لذلك تظل اختبارات الراوتر والاختبارات الوظيفية ضرورية. عند تغيير مخطط البيانات استخدم ترحيلًا جديدًا متوافقًا، ولا تعدّل ترحيلًا سبق تطبيقه.
