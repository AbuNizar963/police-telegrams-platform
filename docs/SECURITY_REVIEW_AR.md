# تقرير مراجعة الأمان والجودة — منصة برقيات الشرطة

## النطاق والمنهجية

رُوجعت أحدث نسخة من `AbuNizar963/police-telegrams-platform` على `origin/main`، وفُحص فرع الهاتف `origin/flutter-mobile-app` والدمجات الأمنية الحديثة، ثم أُنشئت مساحة تكامل محلية `integration/unified-system` مبنية على `origin/main` مع تطبيق الهاتف من فرعه. لم تُدمج الفروع البعيدة، ولم يُنشأ commit أو PR، ولم تُدفع تغييرات إلى GitHub أو تُنشر، ولم يُتصل بقاعدة إنتاج أو تُغيّر أسرار.

هذه مراجعة كود واختبارات محلية وفحص اعتماديات؛ ليست اختبار اختراق خارجيًا ولا شهادة اعتماد أمنية رسمية أو مراجعة بشرية مستقلة لكل إعداد إنتاجي.

## إصلاحات المراجعة الأولى

- **Service Worker:** حُصر الاعتراض في GET لأصول ثابتة فقط، مع رفض التخزين للاستجابات `private` و`no-store` و`no-cache`، وتغيير إصدار cache لحذف النسخ القديمة. اختبارات تمنع التخزين المؤقت للتنقل وواجهات API والتقارير.
- **مهلة تعديل البرقية:** توحّدت قاعدة نافذة 48 ساعة بين الخادم والواجهة في دالة مشتركة واختُبرت حدودها واستثناء مالك النظام.
- **Cache الهاتف:** أضيف سجل محدود لمفاتيح cache الديناميكية كي يمسح التطبيق بيانات الجلسة عند فشل تعداد التخزين الآمن، مع اختبار انحدار.
- **إعداد Supabase:** صُحح اسم المفتاح في التوثيق ليتوافق مع إعداد الخادم، مع التنبيه إلى إبقاء المفتاح الخادمي خارج العميل.
- **اعتماديات Node:** عولجت تنبيهات `body-parser` و`qs` بقيم دنيا مصححة وقفل محدث. أظهر `pnpm audit --audit-level=high` عدم وجود ثغرات معروفة عند الفحص.

## متابعة الدمج الأمني #236

كشف التدقيق المستقل لآخر إصلاح أن فحص نطاق البرقية الفردية لا يغطي استعلامات قائمة البرقيات والتصدير والتقارير ولوحة المؤشرات، كما لم يكن صندوق الإشعارات مقيدًا بجهة المستخدم. لذلك كان يمكن لعضوية ما تزال فعّالة في جدول العضويات أن تواصل قراءة بيانات جهة عُطلت. لم يكن هذا إثباتًا على وجود تسريب فعلي في بيانات الإنتاج؛ لكنه تجاوز مؤكد في مسارات التفويض عند تحقق تلك الحالة.

أُصلح ذلك في مساحة التكامل عبر اشتراط عضوية فعّالة **وجهة فعّالة** ضمن استعلام العضوية نفسه باستخدام العلاقة الداخلية مع `organizations` وشرط `organizations.isActive = true`. وبذلك تستفيد كل المسارات المباشرة التي تعتمد على العضوية من قاعدة واحدة، بما فيها القوائم والتقارير والتصدير والإحصاءات والإحالات وإعدادات الجهة والإشعارات. قُيّد صندوق الإشعارات للعضويات غير العامة بجهة المستخدم الحالية، واستُبعدت الجهات المعطلة وأحفادها من نطاق قراءة المدير الإقليمي، مع الإبقاء على نطاق الإدارة اللازم لاستعادة الجهة المعطلة. لم تتغير صلاحية المسؤول العام المقصودة للوصول الشامل.

أضيفت اختبارات لاستبعاد عضوية جهة معطلة، ولرفض القائمة والتصدير والتقارير والإحصاءات وصندوق الإشعارات عند غياب عضوية فعالة، وللتأكد من استبعاد الفروع المعطلة من نطاق القراءة دون حجب إدارة الاستعادة.

## حدود ما لم يُتحقق منه

- لم تُشغّل اختبارات Supabase/إعادة الترحيلات محليًا؛ Docker وSupabase CLI غير متاحين في البيئة. لم تُستخدم قاعدة الإنتاج بدلًا منها.
- لم تُشغّل GitHub Actions على GitHub لأن التغييرات محلية ولم تُدفع أو تُفتح PR. فُحص تنسيق وصياغة ملفات workflow، لكن يلزم نجاح CI الفعلي على PR، بما فيه Supabase وFlutter وبناء Android على runner مجهّز.
- لا يثبت خلو `pnpm audit` من التنبيهات الحالية غياب ثغرات غير معلنة أو أخطاء إعداد الإنتاج.
- النظام غير منشور من هذه الجلسة، وهذا التقرير ليس شهادة اعتماد أو تصريحًا بأن نشر الإنتاج جاهز قبل اجتياز CI والمراجعة التشغيلية.
