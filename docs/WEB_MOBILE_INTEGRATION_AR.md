# نموذج العمل الموحد للويب والهاتف

## القرار المعماري

الويب وتطبيق Flutter واجهتان لنظام واحد، وليسا خادمين أو قاعدتي بيانات منفصلتين. المستودع على `main` هو مصدر الحقيقة للتطبيقين والخادم والترحيلات والاختبارات. يتصل الهاتف عبر API/tRPC بالخادم نفسه؛ الخادم وحده يقرر الهوية والصلاحيات ونطاق الجهة وحالة البرقية. لا يقرأ تطبيق الهاتف قاعدة Supabase مباشرة ولا يحمل سرًا إداريًا.

## دورة التغيير المقترحة

1. يبدأ التغيير من `main` بفرع feature قصير العمر وPR واحد متكامل.
2. كل تغيير مشترك في API أو البيانات أو الصلاحيات يرفق اختبارات الخادم واختبار عقد Flutter واختبارات الواجهات المتأثرة. تغييرات المخطط تستخدم ترحيلًا جديدًا متوافقًا، لا تعديل ترحيل سبق تطبيقه.
3. يشغّل PR فحوص الويب والخادم وSupabase، ويشغّل فحوص Flutter عند تغيّر `mobile/` أو `server/` أو `shared/` أو `supabase/`. لا يعتمد الدمج إلا بعد نجاح Actions والمراجعات الأمنية وحماية الفرع.
4. إصدار Android عملية منفصلة يدوية من `main` بعد توفر أسرار التوقيع والتحقق من البصمة. لا يُنشر APK موقّع من PR ولا من كل دفع إلى `main`.

## حدود العقد والصلاحيات

يختبر `server/mobileApiContract.test.ts` إجراءات tRPC التي يستدعيها Flutter مقابل `appRouter`. هذا يحمي أسماء المسارات، لكنه لا يثبت تطابق كل الحقول أو التفويض. لذلك يجب أن تغطي اختبارات السلوك الغلاف الفعلي لـ tRPC، واستعادة الجلسة، والأدوار وعضوية الجهة، والقراءات والكتابات والإحالة والتعارض والمرفقات والإشعارات.

الخادم هو المرجع النهائي للصلاحيات؛ واجهات الويب والهاتف ليست حدودًا أمنية. يجب أن يرفض الخادم الجهة المعطلة حتى إن احتفظ العميل ببيانات قديمة دون اتصال. cache لا يقرر التفويض ولا ينبغي أن يعرض كتابة غير مؤكدة كأنها نجحت.

## حالة التكامل المحلي

أُنشئت `integration/unified-system` محليًا من أحدث `origin/main`، ثم أُضيف إليها تطبيق `mobile/` من أحدث `origin/flutter-mobile-app` مع الحفاظ على الخادم و`shared/` وترحيلات `main`. لا يُنصح بدمج فرع الهاتف التاريخي كاملًا إلى `main`؛ تاريخ الفرعين متباعد ويتضمن اختلافات خادم ومخطط وإصدار، لا ملفات Flutter وحدها. أُعيدت مراجعة الدمجات الأمنية الحديثة، وأُصلحت ثغرة نطاق إضافية في #236 كانت تسمح لمسارات القائمة والتقارير والتصدير والإحصاءات وصندوق الإشعارات بالاعتماد على عضوية لا تزال فعالة لجهة معطّلة.

نجح التحقق المحلي على التكامل: `pnpm check`، و**316 اختبارًا في 51 ملفًا**، و`pnpm lint`، و`pnpm check:responsive-shell`، و`pnpm build`، و`pnpm audit --audit-level=high` دون ثغرات معروفة. كذلك نجح تنسيق وتحليل Flutter و**104 اختبارات**؛ تعذر بناء APK محليًا لغياب Android SDK. لا تتوفر Docker أو Supabase CLI لتشغيل اختبارات الترحيلات محليًا.

## التسليم والاعتماد

الملفات في مساحة العمل المحلية `/home/ubuntu/work/police-unified` وعلى الفرع المحلي `integration/unified-system`. لم يُنشأ commit أو PR ولم تُدفع تغييرات، لذلك لم تُشغّل Actions الفعلية على GitHub. يلزم نقل الفرع إلى GitHub وفتح PR وتشغيل Actions على runner مناسب، والتحقق من Supabase/الترحيلات وبناء Android، قبل وصف النسخة بأنها مدموجة أو جاهزة للإنتاج. هذا العمل ليس شهادة اعتماد رسمية.
