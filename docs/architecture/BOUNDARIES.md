# حدود المعمارية وعقود الملكية

## الهدف

هذا المستند يحدد حدود المسؤولية الحالية والمستهدفة دون نقل الملفات دفعة واحدة. يجب أن تكون أي إعادة هيكلة تدريجية وقابلة للتراجع، مع بقاء واجهات المستخدم وواجهات API الحالية متوافقة.

## حدود المجال

- **المصادقة والجلسات:** `server/_core/auth.ts` و`server/_core/loginRateLimit.ts`. لا يُسمح لأي وحدة بتفسير الجلسة أو إنشاء صلاحيات بديلة محليًا.
- **المؤسسات والعضويات:** `server/organization.ts` و`server/organizationScope.ts`. كل عملية متعددة المؤسسات يجب أن تتحقق من المؤسسة المحددة، لا من وجود عضوية عامة فقط.
- **البرقيات ومساراتها:** `server/routers.ts` و`server/db.ts` حاليًا. تُفصل لاحقًا إلى خدمات مجال دون تغيير قواعد العمل في خطوة نقل الملفات نفسها.
- **التخزين:** `server/storage.ts` و`server/storageProvider.ts` و`server/_core/storageRoutes.ts`. مسار الملف ليس بديلًا عن التفويض؛ القراءة والكتابة تتطلبان تحققًا في طبقة API من المستخدم والمالك/المؤسسة.
- **التصدير والتحقق:** `server/telegramExport.ts` وواجهات التحقق في `server/app.ts`. يجب أن تظل بيانات التحقق العامة مقتصرة على ما يحتاجه حامل رمز التحقق.
- **إعدادات الوثائق:** `shared/platformDocumentSettings.ts` و`client/src/lib/platformDocumentSettings.ts`. يجب منع الطباعة/التصدير عند تعذر تحميل إعدادات موثوقة، وإظهار الخطأ للمستخدم.
- **استيراد الجداول:** `client/src/lib/telegramSpreadsheet.ts` و`server/telegramImportWorkbook.ts`. يجب أن تكون مطابقة الأعمدة صريحة، مع أخطاء قابلة للفهم وبيانات صف المصدر، وألا تحذف قواعد التكرار سجلات مختلفة المحتوى.
- **التطبيق المحمول:** مجلد `mobile/` على الفرع `flutter-mobile-app`، وليس ضمن `main`. يجب توثيق كل نقطة API يستخدمها التطبيق وإضافة اختبار عقد على فرع الهاتف قبل تغيير شكل الطلب أو الاستجابة.

## نموذج الملكية متعدد المؤسسات

1. **مالك النظام / مسؤول النظام:** صلاحيات صريحة ومحدودة بالعمليات الإدارية المعتمدة.
2. **مسؤول المؤسسة:** صلاحية ضمن المؤسسة التي يديرها فقط.
3. **المستخدم:** صلاحية بياناته وعملياته وفق قواعد البرقيات.
4. **الأصول المقيدة بالمؤسسة:** الشعارات والملفات والإعدادات يجب ربطها بسجل مؤسسة موجود، والتحقق من العضوية في كل عملية كتابة.
5. **الملفات:** لا تُصدر روابط موقعة لمفتاح عشوائي اعتمادًا على تنسيق المسار وحده؛ يلزم التحقق من النطاق والملكية في نقطة الدخول.

## تنظيم الملفات المستهدف تدريجيًا

```text
client/src/features/
  auth/
  telegrams/
    import-export/
    display/
    documents/
  organizations/
  notifications/

server/
  auth/
  organizations/
  telegrams/
  storage/
  exports/
  notifications/
  verification/

shared/
  schemas/
  domain/
  utils/
```

هذه خريطة مستهدفة وليست تعليمات لنقل جماعي فوري. يجب نقل وحدة واحدة في كل PR مع إبقاء الاستيرادات القديمة مؤقتًا عند الحاجة، ثم حذفها بعد نجاح CI واختبارات الاستخدام.

## بوابات القبول

- لا دمج دون نجاح التنسيق، وفحص الأنواع، والاختبارات، والبناء، وCodeQL وSecret Scanning.
- تغييرات الصلاحيات تتطلب اختبارات رفض الوصول بين مؤسستين مختلفتين.
- تغييرات الاستيراد تتطلب حالات رؤوس مفقودة، وصفوف تالفة، وتكرارات متطابقة وأخرى مختلفة.
- تغييرات التصدير تتطلب حالة إعدادات مفقودة أو غير صالحة ورسالة واضحة للمستخدم.
- تغييرات CSS أو الخطوط أو الشعارات أو العلامة المائية أو مقاسات الصفحة أو إعدادات CSP تتطلب اختبارًا بصريًا فعليًا لصفحة الطباعة وملف PDF وصورة PNG على الأقل؛ نجاح CI وحده لا يثبت تطابق المظهر.
- يجب مقارنة مخرجات مرجعية قبل/بعد التغيير مع التحقق من اتجاه RTL، وخط Cairo، وهوامش A4، ووضوح الشعارات والصور والعلامة المائية وعدم قص المحتوى.
- تغييرات قاعدة البيانات تتطلب مراجعة الترحيل واختبارًا محليًا، ولا تُطبق على الإنتاج تلقائيًا من هذا المستند.
