# نموذج تطوير الويب وتطبيق الهاتف على فرعين

## القرار المعماري

الويب وتطبيق Flutter عميلان للنظام نفسه، وليسا خادمين أو قاعدتي بيانات منفصلتين. يحتوي `main` موقع الويب وخادم API ومخطط البيانات. ويحتوي `flutter-mobile-app` تطبيق Flutter وفحوصه، إلى جانب نسخة متوافقة من ملفات الخادم والأنواع المشتركة اللازمة لاختبار العقد. يتصل الهاتف بخادم الإنتاج نفسه عبر API/tRPC؛ ولا يتصل بقاعدة Supabase مباشرة ولا يحمل سرًا إداريًا.

يفصل هذا الترتيب دورة تطوير تطبيق الهاتف عن نشر الويب، لكنه لا يفصل المصادقة أو الصلاحيات أو بيانات البرقيات. يظل الخادم في `main` المرجع النهائي للتحقق من الهوية والعضوية والجهة وحالة البرقية.

يُحتفظ بتعريف `.github/workflows/flutter-mobile.yml` في `main` لأن GitHub يشترط وجود workflow الذي يستخدم `workflow_dispatch` في الفرع الافتراضي. لكن محفزات push وpull request، وشروط بناء APK الموقّع، مقيدة بفرع `flutter-mobile-app`؛ لا يؤدي push إلى `main` إلى بناء تطبيق الهاتف أو إصدار APK.

## حدود الفروع ومسؤولياتها

- **`main`:** مصدر نشر الويب وAPI. تبقى فيه إصلاحات أمان صلاحيات الجهات، وحماية Service Worker، وتحديثات الاعتماديات التي أُدخلت في PR #237.
- **`flutter-mobile-app`:** فرع تطوير الهاتف. يحتوي تطبيق `mobile/` وFlutter CI واختبار توافق إجراءات tRPC مع الخادم.
- **رأس الفرع السابق:** يُحفظ قبل التحديث في وسم استرجاع `archive/flutter-mobile-app-pre-separation-0341b018`؛ الوسم ليس فرعًا إضافيًا.

لا تُحذف واجهات API التي يحتاج إليها الهاتف من الخادم لمجرد إخراج مجلد التطبيق من `main`. أي تغيير في API أو المخطط أو الصلاحيات يجب أن يحافظ على التوافق مع الهاتف، ويُختبر على الفرعين.

## دورة التغيير

1. تغييرات الويب والخادم تبدأ من `main` وتُراجع عبر PR إلى `main`؛ نشر Vercel للإنتاج مرتبط بهذا الفرع.
2. تغييرات واجهة Flutter تبدأ من `flutter-mobile-app`. تعمل فحوص Flutter والويب/الخادم وتحليل CodeQL وفحص الأسرار ومراجعة الاعتماديات على الفرع.
3. عند تعديل عقد API، حدّث أو اختبر المستهلكين في الفرعين. يجب أن تظل قواعد التفويض في الخادم؛ إخفاء زر في الهاتف أو تخزين محلي لا يمثل حاجزًا أمنيًا.
4. إصدار Android إجراء يدوي منفصل من `flutter-mobile-app` بعد نجاح الفحوص وتوفر إعدادات التوقيع والجاهزية. لا ينشر push أو PR إصدارًا عامًا تلقائيًا.
5. لا تدمج فرع الهاتف إلى `main` لمجرد الحاجة إلى النشر على Android؛ تُنشر نسخة الهاتف من فرعه. لا تُدمج تغييرات الخادم من `main` إلى فرع الهاتف إلا بعد مراجعة التوافق وحل التعارضات واختبار الطرفين.

## التوافق والبيانات

يوجد اختبار عقد ساكن على فرع الهاتف يطابق أسماء إجراءات tRPC التي يستدعيها Flutter مع `appRouter`. هذا الاختبار لا يثبت تطابق الحقول أو الصلاحيات أو السلوك الكامل؛ لذلك تظل اختبارات الراوتر والاختبارات الوظيفية ضرورية. عند تغيير مخطط البيانات استخدم ترحيلًا جديدًا متوافقًا، ولا تعدّل ترحيلًا سبق تطبيقه.

## حالة الفصل والنشر

الالتزام `b66cea9` (دمج PR #237) هو أساس النسخة المصلحة التي حُفظت في فرع الهاتف الجديد. يتضمن أيضًا إصلاحات أمان وخادم وويب غير مرتبطة بمجلد Flutter؛ ستبقى تلك التغييرات في `main` عند إزالة عميل الهاتف. إصدار Android الحالي `v1.0.121-build.695` يبقى منشورًا، ولا تُحذف إصدارات GitHub Releases تلقائيًا عند فصل الشيفرة.

قبل اعتماد الفصل، يجب أن ينجح PR إزالة التطبيق من `main` على GitHub، ثم يُختبر نشر الويب/API بعد الدمج. لا يُعد هذا الإجراء شهادة رسمية أو إثباتًا مطلقًا لخلو النظام من الثغرات.
