# دليل التشغيل والاستعادة

هذا الدليل جزء من تسليم منصة البرقيات. لا يعتبر النسخ الاحتياطي ناجحًا إلا بعد **استعادة فعلية في بيئة معزولة** والتحقق من السجلات والمرفقات.

## 1. ملكية الحسابات

- حساب GitHub والمستودع الخاص مملوكان للمالك.
- حساب Supabase ومشروعه يجب أن يكونا تحت حساب المالك، وليس حساب مطور أو فريق غير معتمد.
- حساب Vercel يجب أن يكون ضمن **Personal Account** الصحيح، وليس نطاق `hadirapp`.
- بعد التسليم، أزل أي عضو أو رمز وصول غير مطلوب ودوّر المفاتيح التي استُخدمت أثناء الاختبار.

## 2. تصنيف متغيرات البيئة

### عامة للمتصفح

```text
VITE_SUPABASE_URL
VITE_SUPABASE_PUBLISHABLE_KEY
```

تظهر هذه القيم في حزمة المتصفح، ولذلك لا تمنح أمانًا بمفردها. يجب أن تكون RLS وStorage policies مفعلة ومختبرة.

### للخادم فقط

```text
SUPABASE_URL
SUPABASE_PUBLISHABLE_KEY
DATABASE_URL
JWT_SECRET
OWNER_OPEN_ID
BUILT_IN_FORGE_API_URL
BUILT_IN_FORGE_API_KEY
```

لا تضع مفتاح `SUPABASE_SECRET_KEY` أو service-role key أو كلمات مرور قاعدة البيانات في `VITE_*` أو GitHub أو المستودع.

## 3. نشر قاعدة Supabase

في بيئة اختبار جديدة:

```bash
supabase login
supabase link --project-ref YOUR_PROJECT_REF
supabase db reset
supabase test db
```

بعد مراجعة النتائج:

```bash
supabase db push
```

لا تطبق SQL يدويًا من Dashboard بعد اعتماد migrations. أي تغيير لاحق يجب أن يكون migration جديدًا ومراجعًا.

## 4. النسخ الاحتياطي لقاعدة البيانات

استخدم اتصالًا محميًا من Supabase واحفظ الناتج في مخزن مشفر خارج المستودع:

```bash
pg_dump "$DATABASE_URL" \
  --format=custom \
  --no-owner \
  --no-privileges \
  --file="backup-$(date -u +%Y%m%dT%H%M%SZ).dump"
```

احتفظ بسجل:

- وقت النسخ بصيغة UTC.
- اسم البيئة والمشروع.
- حجم الملف وSHA-256.
- مدة التنفيذ والنتيجة.
- مكان التخزين وسياسة الاحتفاظ.

## 5. نسخ المرفقات

نسخة قاعدة البيانات لا تكفي؛ يجب نسخ Storage bucket الخاص بالمرفقات أو استخدام ميزة النسخ/التصدير التي يوفرها مزود التخزين. قبل النسخ:

1. صدّر قائمة `telegram_attachments` ومسارات Storage.
2. انسخ الملفات مع metadata النوع والحجم وchecksum إن وجد.
3. قارِن عدد المسارات وعدد الملفات.
4. افحص سجلات `attachment.orphaned` وأنشئ قائمة تنظيف منفصلة؛ لا تحذفها تلقائيًا قبل مراجعة المسؤول.

## 6. اختبار الاستعادة

في مشروع أو قاعدة معزولة:

```bash
createdb police_telegrams_restore
pg_restore \
  --dbname="$RESTORE_DATABASE_URL" \
  --clean \
  --if-exists \
  --no-owner \
  backup-YYYYMMDDTHHMMSSZ.dump
supabase test db
```

معايير النجاح:

- عدد البرقيات والمستخدمين وسجلات التدقيق مطابق للمصدر.
- يمكن قراءة برقية ومرفق من جلسة مصرح بها.
- لا يمكن لمستخدم من جهة أخرى قراءة البرقية أو المرفق.
- كل الملفات المصدرة لها checksum مطابق.
- تعمل migrations اللاحقة من النسخة المستعادة.

وثّق النتيجة في سجل الاستعادة، ولا تعتبرها ناجحة بمجرد اكتمال `pg_restore`.

## 7. المراقبة والاستجابة

راقب على الأقل:

- أخطاء HTTP 5xx وزمن `/api/health`.
- فشل إنشاء البرقية وفشل حفظ المرفقات.
- أحداث `attachment.orphaned`.
- استهلاك قاعدة البيانات وStorage وحدود الخطة.
- فشل Google/Supabase Auth وتجديد الجلسات.

عند حادثة:

1. عيّن معرف حادثة ووقت UTC.
2. أوقف الوصول أو دوّر المفتاح المتأثر عند الحاجة.
3. لا تحذف سجلات التدقيق.
4. خذ نسخة قبل الإصلاح إن أمكن.
5. طبّق الإصلاح عبر commit وmigration، ثم اختبر في Preview.
6. وثّق السبب والإجراء وقرار استعادة الخدمة.

## 8. بوابة الإنتاج

لا يُدمج فرع التسليم في `main` قبل اكتمال اختبار Supabase المحلي/الاختباري، واختبار عزل جهتين، واختبار استعادة موثق، وضبط متغيرات Vercel في الحساب الشخصي الصحيح.
