# خطة تحويل تخزين منصة البرقيات إلى تخزين مركزي

**الحالة:** تصميم وتنفيذ مرحلي على فرع مستقل  
**الفرع:** `feature/centralized-storage`  
**الفرع المرجعي:** `main`  
**النطاق:** مرفقات البرقيات وشعارات الجهة، مع إبقاء قاعدة البيانات الحالية مستقلة عن مزود تخزين الملفات.

## الهدف

إنشاء نقطة تخزين مركزية واحدة تخدم جميع المستخدمين المخولين، مع عدم ربط منطق المنصة بمزود واحد. يجب أن يتمكن المسؤول المخول من إدارة الملفات مركزيًا، بينما تبقى صلاحيات القراءة والتنزيل مفروضة من الخادم، لا من واجهة المستخدم أو من معرفة رابط الملف.

هذا الفرع لا ينقل بيانات حقيقية ولا يغير إعدادات الإنتاج تلقائيًا. أي انتقال إلى خادم الوزارة أو مخزن محلي يتطلب بيئة معتمدة، ونسخًا احتياطيًا، وتجربة نقل واستعادة، وموافقة الجهة المالكة للبيانات.

## الوضع الحالي الذي ظهر في مراجعة الشيفرة

- أصبح `server/storage.ts` يستخدم واجهة المزود في `server/storageProvider.ts` بدل استدعاء Supabase Storage مباشرة.
- المحوّل الفعّال الوحيد حاليًا هو Supabase؛ لم تتم إضافة إعدادات لمزود بديل أو نقل بيانات.
- تنزيل الملفات يمر عبر `/api/storage/*)، ويتحقق الخادم من هوية المستخدم ثم يصدر رابطًا موقعًا مؤقتًا.
- صلاحية الموظف في دالة `canAccessStorageKey` مقيدة بمسار مرفقات البرقيات الخاصة به، بينما يستطيع المدير الوصول إلى مفاتيح البرقيات الصالحة.
- رفع شعارات الإدارة يستخدم مسارًا منفصلًا ويعيد رابطًا موقعًا.
- اختبارات صلاحيات المسارات موجودة، لكن اختبارات عقد مستقلة للمحوّل لم تُضف بعد.
- آخر تشغيل موثق لـ GitHub Actions هو CI رقم 216، وقد اكتمل بنجاح على commit `9bdcd240bcededec1b0a7d81ed40d9e63c125e05`. يجب إعادة تشغيل التحقق بعد أي تعديل لاحق.

## التصميم المستهدف

1. **واجهة موحدة للتخزين:** عقد داخلي واضح لعمليات رفع الملف، وإصدار رابط تنزيل مؤقت، والتحقق من وجود الملف، وحذفه عند السماح بذلك.
2. **محوّل مزود (Adapter):** يبقى Supabase هو المزود الافتراضي في المرحلة الأولى، ويُضاف لاحقًا محوّل متوافق مع S3 عند اختيار خادم الوزارة أو NAS/Object Storage متوافق.
3. **مفاتيح ثابتة:** تخزن قاعدة البيانات مفتاح الملف ومعرّفه المنطقي، لا رابطًا مؤقتًا. تصدر الروابط عند الطلب وبمدة قصيرة.
4. **تفويض مركزي:** جميع عمليات القراءة والكتابة والحذف تمر عبر الخادم وتتحقق من الدور وملكية البرقية. لا تُمنح الواجهة مفاتيح إدارية أو أسرار مزود التخزين.
5. **فصل الإعدادات:** اختيار المزود ونقطة النهاية والحاوية/المساحة من متغيرات بيئة خادمية؛ لا تتضمن المستودعات أسرارًا.
6. **التوافق:** لا تتغير مسارات API الحالية أو شكل استجاباتها دون اختبارات توافق؛ ولا تُكسر الملفات القديمة أو الروابط المخزنة.
7. **التدقيق:** تسجيل أحداث الرفع والتنزيل والحذف والنتيجة وهوية الفاعل ومعرّف البرقية، دون تسجيل محتوى الملفات أو أسرار الوصول.
8. **المرونة المستقبلية:** يسمح العقد باستضافة الملفات في مركز بيانات الوزارة دون تعديل منطق البرقيات، بشرط توافق المزود مع الواجهة المعتمدة.

- [ ] توثيق جميع المستدعين ومسارات تخزين البيانات الوصفية والروابط القديمة.

- [ ] التأكد من عدم تخزين روابط موقعة دائمة، مع خطة توافق للبيانات القديمة.

### المرحلة 2 — فصل المزود عن منطق التطبيق
- [x] نقل التعامل المباشر مع Supabase إلى محوّل مستقل.
- [x] إبقاء الدوال العامة الحالية كواجهة توافق مؤقتة لتجنب تعديل المستدعين دفعة واحدة.

### المرحلة 3 — دعم التخزين المركزي القابل للاستضافة الذاتية
- إضافة محوّل S3 متوافق عند توفر بيئة اختبار معتمدة.
- إعداد تحقق اتصال وصلاحيات عند بدء التشغيل دون كشف الأسرار.
- اختبار الرفع والتنزيل والحذف والتعامل مع انقطاع الشبكة وانتهاء الروابط.

### المرحلة 4 — نقل تجريبي دون فقد
- جرد الملفات وحساب أعدادها وأحجامها وبصمات SHA-256.
- نسخ تجريبي إلى الوجهة الجديدة والتحقق من كل ملف والبيانات الوصفية والصلاحيات.
- اختبار خطة رجوع واضحة قبل تحويل أي حركة إنتاجية.
- تنفيذ النقل الفعلي فقط بعد اعتماد رسمي وخطة صيانة ونسخ احتياطي.

## شروط القبول

- لا توجد أسرار أو مفاتيح وصول ضمن Git.
- لا يستطيع المستخدم غير المخول تجاوز التفويض بتغيير مفتاح الملف أو عنوان URL.
- الملفات القديمة تظل قابلة للوصول خلال الانتقال.
- اختبارات الصلاحيات والعقد وTypeScript والبناء وActions ناجحة قبل الدمج.
- لا يتم تحويل إنتاج المنصة أو حذف المصدر القديم قبل نجاح التحقق وخطة الرجوع.
- توثق جميع التغييرات التشغيلية وإعدادات النشر المطلوبة.

## تنبيه تشغيلي

وجود RAID أو نسخة متطابقة على خادم واحد لا يعوض النسخ الاحتياطي المستقل. يلزم تحديد أهداف الاستعادة (RPO/RTO)، والتشفير أثناء النقل والتخزين، وإدارة مفاتيح تحت سيطرة الجهة المالكة، واختبارات استعادة دورية.
