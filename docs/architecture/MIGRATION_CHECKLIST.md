# قائمة مراجعة تغييرات قاعدة البيانات وعقود API

## قبل تعديل قاعدة البيانات

- [ ] هل تغيرت `drizzle/schema.ts`؟ هل يوجد ترحيل مقابل في `supabase/migrations/`؟
- [ ] هل الترحيل قابل للتطبيق على قاعدة بيانات تحتوي بيانات فعلية؟
- [ ] هل يتطلب التغيير فهرسًا أو قيدًا فريدًا أو قيد ملكية/مؤسسة؟
- [ ] هل أُضيف اختبار قاعدة بيانات يغطي النجاح والفشل وحدود المؤسسة؟
- [ ] هل يتطلب النشر خطوة منفصلة أو ترتيبًا محددًا لتوافق التطبيق القديم والجديد؟
- [ ] هل تمت مراجعة خطة التراجع، خصوصًا عند حذف أو إعادة تسمية عمود؟

## قبل تعديل عقد API

- [ ] يوجد مخطط تحقق واضح لمدخلات الطلب.
- [ ] يتم التحقق من الصلاحيات ونطاق المؤسسة على الخادم، وليس في الواجهة فقط.
- [ ] أحجام النصوص والملفات والصفوف محددة عند نقطة الدخول.
- [ ] رسائل الأخطاء لا تكشف أسرارًا أو بيانات مؤسسة أخرى.
- [ ] تم فحص الاستخدامات في الويب والمحمول وأي مستهلك آخر.
- [ ] أُضيفت اختبارات توافق للمدخلات القديمة والجديدة عند الحاجة.

## ميزانيات أولية يجب مراجعتها مع بيانات الإنتاج

| المسار | الحد الحالي المعروف | مراجعة مطلوبة |
|---|---:|---|
| معاينة ملف Excel | 22 MB | اختبار الذاكرة وزمن التحليل |
| استيراد صفوف البرقيات | 50 MB | التحقق من عدد الصفوف والحقول قبل الإدخال |
| رفع مرفق | 16 MB | تحقق محتوى الملف والمهلة والتنظيف عند الفشل |
| رفع شعار | 8 MB لجسم الطلب، و5 MB لفحص الملف | توحيد الحدود وتوثيق الفرق بين ترميز Base64 وحجم الملف |

هذه حدود الكود الحالية التي يجب اختبارها، وليست توصية برفعها. يجب ضبط الحدود وفق قياسات واقعية وقيود منصة النشر.

## إدارة الانحراف بين المخطط والترحيلات

- يجب أن يرفق كل تغيير مخطط بترحيل واضح ومراجع.
- يجب تشغيل اختبارات الترحيلات على قاعدة محلية نظيفة قبل الدمج.
- يجب مراجعة تغييرات البيانات المقيدة بالمؤسسة بشكل منفصل.
- لا تُنفذ ترحيلات إنتاج أو تغييرات بيانات حقيقية دون موافقة صريحة وخطة استرجاع.
